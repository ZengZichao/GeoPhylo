# Release procedure (public GitHub repository + Zenodo DOI)

English | [中文](RELEASE.zh-CN.md)

This document describes only the two release steps that are **executed
manually by the maintainer**. All repository metadata is already prepared; the
only value left to fill in is the `CITATION.cff` placeholder once Zenodo has
minted the concept DOI (see "Paste-in locations" below).

The version is currently `0.1.0` and must agree in the following five places
(re-check before releasing): `geophylo/_version.py`, `pyproject.toml`,
`CITATION.cff`, `.zenodo.json`, and the version heading of `CHANGELOG.md`
(`test_version_agrees_across_release_files` in `tests/test_packaging.py` pins
exactly these five).

---

## Step 1 — Publish the repository and create the release

1. GitHub → target repository → **Settings → General → Danger Zone → Change
   repository visibility → Make public**. Before making it public, confirm the
   working tree is clean, i.e. `git status --short` prints nothing.
2. Tag and publish the release (local commands, either variant; the tag name is
   the version string prefixed with `v`):

   ```bash
   VERSION=0.1.0
   git tag -a "v${VERSION}" -m "GeoPhylo ${VERSION}"
   git push origin main "v${VERSION}"
   gh release create "v${VERSION}" --latest --title "GeoPhylo ${VERSION}" --generate-notes
   ```

   Or on the web UI, **Releases → Draft a new release**: set Tag to
   `v${VERSION}` (i.e. `v` + the version string), Target `main`.

3. **`.zenodo.json` must be present in the commit the tag points to** (Zenodo
   reads the release snapshot, not the branch HEAD). Committing first and then
   tagging, as above, satisfies this.

## Step 2 — Mint the Zenodo DOI

1. Sign in at <https://zenodo.org/account/settings/github/> with the same
   GitHub account and switch on **repository synchronization** for
   `ZengZichao/GeoPhylo`. If the release already exists and the switch was
   turned on afterwards, go back to the release page and click the Zenodo badge
   (or select the release under `zenodo.org → Your uploads → New upload →
   Import`) to import it once more.
2. Zenodo pre-fills the draft from `.zenodo.json`; its `version` and
   `publication_date` are overridden by the tag metadata, which is normal. Do
   **not** write a `conceptdoi` key into `.zenodo.json` — both DOIs are
   generated by Zenodo.
3. Review the draft manually, then click **Publish**, and record both numbers:
   - **Concept DOI** `10.5281/zenodo.XXXXXXXX`: version-independent, for
     long-term citation;
   - **Version DOI**: specific to this release, for exact reproducibility.
4. License note: the repository artifacts also contain **CC-BY-4.0** ICS
   snapshot data, but a Zenodo record accepts only a single `license`, so the
   record is filed as `MIT`. Attribution on the data side is carried jointly by
   three places: the `notes` field of `.zenodo.json`, the in-repo `NOTICE`, and
   `LICENSES/CC-BY-4.0.txt`. Keep `notes` when publishing.

## Paste-in locations

| Target | Location | What to fill in |
| --- | --- | --- |
| `CITATION.cff` | `identifiers[0].value` (currently `10.5281/zenodo.REPLACE_AT_FIRST_RELEASE`) | the Concept DOI |
| Optional | top-of-`README.md` badge, reference sections of `docs/user-guide.*.md` | a Version DOI badge `https://zenodo.org/badge/DOI/<version-doi>.svg` |

Once filled in, also delete the `REPLACE_AT_FIRST_RELEASE` comment lines in
`CITATION.cff`. Before publishing each new release, repeat Step 2: Zenodo
derives a new version record while the Concept DOI stays unchanged.

## Post-release verification

```bash
# Gate suite: command verbatim from the authoritative definition at the top of
# .github/workflows/ci.yml (--mpl is mandatory; experimental tests must not be
# deselected, otherwise the radial path escapes the re-check).
pip install -e ".[test]"
MPLBACKEND=Agg pytest -m "not performance" -v --mpl \
    --mpl-baseline-path=tests/baseline_images

# Clean-room check: must be done in an **isolated venv**, not with the
# interpreter used by `pip install -e` above — that one already put the source
# tree on sys.path, so check_wheel.py's `from geophylo import Timescale` would
# import the sources instead of the artifact and the "clean install" verdict
# would be void (same approach as the clean-room job in ci.yml).
python -m build
python -m venv clean-room
clean-room/bin/pip install --upgrade pip
clean-room/bin/pip install dist/*.whl
clean-room/bin/python tests/packaging/check_wheel.py dist

grep -R "geophylo/geophylo\|REPLACE_AT_FIRST_RELEASE" . --exclude-dir=.git \
    --exclude=RELEASE.md --exclude=CHANGELOG.md   # expect no output outside this file and the changelog
```
